## 계산 (책 패키지 `MultiFactor 0.3.3` 방식을 기준으로 함)

책 본문의 설명과 패키지 코드는 **서로 다르다**. 책에 실린 숫자는 패키지가 만든 것이므로 패키지 쪽을 기준으로 삼았다.

- **모멘텀 주가**: 패키지는 전일·주간·월간·**3개월**·연간 5개 기간(거래일 2/5/20/60/240개 전 종가 대비)의 평균이고, 데이터가 모자란 기간은 빼고 평균한다. 책 본문은 3개월이 없는 4개 기간(2/6/21/241)으로 설명한다. `MOM_VARIANT="text"` 로 본문 방식을 고를 수 있다.
- 모멘텀 거래량 = 5일 평균 거래량 / 20일 평균 거래량 − 1. 밸류 = PER, PBR(연간 K-IFRS 연결, 영업이익이 빈 추정치 행 제외, 최신 확정값). 퀄리티 = 전분기 대비 매출·영업이익·순이익 증가율 + ROE(분기 연결, 추정치 제외).
- **순위(%)** = 대상 안의 순위 ÷ 종목 수 × 100. **동점은 평균 순위**(공동 2위면 2.5, 패키지의 pandas `rank` 기본값). 순위는 **반올림하지 않은 값**으로 매긴다(저장 시에만 소수 둘째 자리로 반올림).
- **값이 없으면 그 지표의 중앙값으로 채운다**(패키지 방식, 결과에 `filled:지표` 표시). 종합점수 = 선택 지표 순위의 평균(낮을수록 상위). 스타일은 같은 8개 순위 중 일부만 평균: 가치 성장(밸류+퀄리티), 추세 성장(모멘텀+퀄리티), 역발상(밸류+모멘텀).
- **종목 선정**: 패키지와 같은 기준 — 시총 1천억 원 이상, 주가 1천 원 이상, 목록의 당일 거래량 2천 주 이상, 우선주(코드 끝자리 5·7·9·K) 제외, 이름에 스팩·리츠·리얼티·인프라·유전·벤처 포함 제외, 코넥스 제외.

### 책 패키지와 의도적으로 다르게 한 점 (결과 JSON의 `method.deviations` 에도 기록)

| # | 패키지 | 우리 | 이유 |
|---|---|---|---|
| 1 | PER·PBR 이 음수면 가장 싼 값으로 보아 **상위 순위**, 적자 기업은 PER 이 빈 값으로 와서 중앙값으로 채워 **중간 순위** | PER·PBR 이 0 이하이거나, 비었는데 EPS·BPS 가 0 이하(적자·자본잠식)이면 **최하위** | 삼성SDI·LG화학·SK이노베이션 모두 EPS<0 이고 PER 이 NaN 임을 확인(2026-10-19). 적자 기업이 중간 순위를 받는 것은 부적절 |
| 2 | 증가율 = (현재−전)/전. 전분기가 적자면 **부호가 뒤집힘**(적자→흑자가 −로 나옴) | 분모에 절댓값, `base_nonpositive` 표시 | LG화학 영업이익증가 패키지 −1306% vs 우리 +1306% |
| 3 | `Market in [KOSPI, KOSDAQ]` 만 → **KOSDAQ GLOBAL 제외**(알테오젠·에코프로·에코프로비엠 등 50종목) | KOSDAQ GLOBAL 포함 | 코스닥 대형주가 통째로 빠지는 것은 의도로 보이지 않음 |
| 4 | 이름에 '리츠'가 있으면 제외 → **메리츠금융지주(시총 21조 원)도 제외** | '메리츠'는 리츠로 보지 않음 | 명백한 오탐 |
| 5 | 재무가 전혀 없는 종목도 중앙값으로 채워 남김 | 제외 | 정보가 없는 종목이 중간 순위를 받는 것을 피함 |

그 밖에 패키지는 `import` 시 파이썬 로그·경고를 전역으로 꺼 버린다(우리는 쓰지 않으므로 무관).

## 책 패키지와의 비교 (2026-10-19, 시총 상위 60종목, 같은 입력 데이터)

패키지 소스를 pip 설치 없이 파일 그대로 불러와 **한 번 받은 같은 데이터**를 양쪽에 공급해 비교했다(저녁 시간대에 당일 종가가 계속 바뀌는 영향을 제거).

- **`strict` 모드(패키지와 똑같이 계산)**: 원본 지표 8개 모두 소수 둘째 자리까지 **전부 일치**. 지표별 순위 차이 ≤ 0.003(반올림), 종합점수 차이 ≤ 0.005. 최종 순위 상관계수 0.9999(기본)·1.0(가치 성장·추세 성장·역발상). 상위 5·10·20개 **전부 동일**. 순위가 정확히 같은 종목은 기본 48/60 — 나머지는 수학적으로 동점인 종목을 패키지는 부동소수점 오차로 갈라 놓고 우리는 평균 순위로 둔 차이(최대 0.5순위).
- **기본 모드(위 5개 차이 적용)**: 순위 상관 0.94(기본)·0.935(가치 성장)·0.94(추세 성장)·0.985(역발상), 상위 5개 동일, 상위 10개 중 10개(기본). 차이는 전분기 적자 종목(LG화학, LG에너지솔루션, 한화시스템, 삼성SDI 등)과 적자 PER 종목에 몰려 있다. 이것이 의도한 차이다.
- 종목 선정: 60개 중 57개 일치. 패키지에는 KOSDAQ GLOBAL(알테오젠 등)이 없고, 그 자리를 포스코인터내셔널·대한항공·현대오토에버가 채웠다.

## 공시와의 대조 (2026-10-19, GitHub Actions, 시총 상위 20종목)

네이버(FDR)의 분기 재무를 금감원 OpenDART 공시(`fnlttSinglAcntAll`, 연결 우선)와 비교했다. 분기 금액 허용오차는 ±1억 원 또는 ±0.3%.

| 항목 | 일치/비교 | 비고 |
|---|---|---|
| 당기순이익(총) | **40 / 40** | 네이버의 당기순이익은 **비지배지분을 포함한 총 당기순이익**(지배주주분과는 14/40만 일치) |
| 영업이익 | 35 / 40 | 불일치 5건: LG에너지솔루션 2, 삼성SDI 2, SK 1 |
| 매출액 | 28 / 32 | 불일치 4건: SK스퀘어 2, LG에너지솔루션 2. 은행·보험 4곳(8건)은 공시 계정 구조가 달라 비교 못 함 |

- **일치하는 종목은 증가율도 일치**(20종목 중 16곳이 매출·영업이익·순이익 증가율 모두 같음).
- 불일치는 **정의 차이**로 보인다(원인은 확인하지 않음): LG에너지솔루션·삼성SDI 영업이익은 공시와 크게 다르고, SK스퀘어는 네이버 매출이 공시 매출의 약 29배(86,314억 vs 3,003억; 지분법손익 등을 포함한 영업수익일 가능성). 그 결과 **SK스퀘어의 매출증가율은 네이버 127% vs 공시 9%**다. 이 점수에서 SK스퀘어가 상위인 이유 중 하나가 이 정의 차이일 수 있어 해석 시 주의해야 한다.
- 계정 매칭은 표준계정 ID(`ifrs-full_Revenue`, `dart_OperatingIncomeLoss`, `ifrs-full_ProfitLoss`)를 우선하고 이름으로 보완했다(가이드에 ID 목록이 없어 응답에서 찾음). 실제로 맞춘 계정은 결과 표에 기록되며, 엉뚱한 계정을 맞춘 흔적은 보이지 않았다. 다만 이것이 모든 종목에서 옳다는 보장은 아니다.
- **미검증(대조하지 않음)**: PER·PBR·ROE·거래량. 공시 원자료로 같은 정의를 재현하기 어렵다.

## 주가 입력의 불확실성 (2026-10-19, 이 PC에서 확인)

네이버(FDR)와 야후(yfinance) 종가를 10종목에서 비교했다(클라우드에서는 야후가 요금 제한 `YFRateLimitError` 로 막혀 이 PC에서만 실행).
- 같은 날 종가가 0.5% 이내로 맞는 비율은 대부분 90~95%(120일 중 108~114일). 삼성바이오로직스는 12/120(분할 후 수정주가 처리 차이로 보임, 미확인).
- **정상 거래일에도 최대 약 3.5% 차이**(삼성전기 10/15: 1,122,000 vs 1,163,000). 모멘텀 주가 평균은 종목별로 0.7~1.9%p, 삼성전기는 4.95%p 달랐다.
- 어느 쪽이 공식 종가인지는 **공식 자료가 없어 판단하지 못했다**(KRX 정규장 종가 vs 대체거래소 포함 종가일 수 있다는 가설뿐, 미확인).
- 또한 장 마감 후에도 네이버의 당일 종가가 계속 바뀐다(SK스퀘어 761,000 → 782,000 → 795,000, 같은 날 저녁). 이 때문에 **정산된 전 거래일 기준으로 계산하도록 토요일 오전에 실행**한다(2026-10-19 주가 값이 클라우드(16:46)와 PC(16:22)에서 달랐던 것도 같은 이유로 추정, 원인 확인은 아님).
- 결론: 모멘텀 값은 대체로 ±1~2%p, 최대 5%p 정도의 입력 불확실성이 있어, 순위가 가까운 종목끼리의 앞뒤는 신뢰하기 어렵다.

## 미국 (2026-10-19, 수신 시험만 했고 구현하지 않음)

책의 미국판 패키지(`MultiFactorUS`)는 야후(`yfinance`)에 의존한다. 소스를 읽어 확인한 점과 GitHub Actions 수신 시험 결과:

- **책 패키지의 미국 퀄리티 정의가 국내와 다르다**: "영업이익 증가율"은 증가율이 아니라 `operatingMargins`(영업이익률)이고, 매출·순이익 증가율은 야후가 주는 전년 동기 대비 값이다. 책 표에서 엔비디아 값이 0.65(=영업이익률)로 나오는 것과 일치한다. 같은 이름의 지표지만 국내와 다른 정의다.
- 밸류·퀄리티는 종목마다 `Ticker.info`(종목당 1회 호출)를 쓴다. 종목 선정은 제3자 CSV(GitHub `top-us-stock-tickers/sp500.csv`)이고 제외 규칙은 없다.
- **수신 시험 결과**: S&P 500 목록(FDR→위키백과) 503개 수신 가능. **야후는 클라우드에서 막힘** — 일별 주가는 빈 결과, `Ticker.info` 429(`YFRateLimitError`), 분기 재무 빈 결과(규모 시험은 연속 10회 실패로 즉시 중단). 즉 책 방식을 Actions 에서 그대로 쓸 수 없다.
- **대체 출처 시험**: SEC EDGAR(`www.sec.gov/files/company_tickers.json`)는 **403**(User-Agent 형식 또는 접근 정책 문제로 추정, 원인 미확인), Stooq CSV 는 CSV 가 아닌 응답(원인 미확인). **FinanceDataReader 의 미국 주가(`fdr.DataReader('AAPL')`)는 받아진다**(449행, 출처는 확인하지 않음).
- 결론: 클라우드에서 확인된 미국 입력은 **종목 목록과 주가뿐**이다. 재무(PER·PBR·ROE·증가율)를 받을 경로는 아직 없다. 그래서 미국 멀티팩터는 **구현하지 않았고, 이번 PR 범위에서 보류**했다(시험 코드도 PR 에서 제외).

## 결과는 공개하지 않는다 — 약관 조사와 보안 확인 (2026-10-19)

**결정**: KRX·네이버에서 받은 데이터의 파생 값을 공개해도 된다는 근거를 찾지 못해(아래 조사), 결과를 저장소·Pages·아티팩트에 올리지 않고 **본인 인증 뒤에만 읽는 비공개 Firestore** 에 둔다.

**약관 조사 요약**(원문 확인, 법률 자문 아님)
- KRX [홈페이지 이용약관](https://data.krx.co.kr/contents/MDC/INFO/informationController/MDCINFO003.cmd): 제10조 ②호 자동화 수단의 무단 수집·복제·배포 금지, 제12조 ②항 사전 허락 없는 복제·배포·전송 금지, 마켓데이터 상품은 별도 약관(제12조의2, 미확인).
- 코스콤 [정보이용정책(2024-01-01)](https://data.krx.co.kr/inc/datasale/Market%20Data%20Usage%20Polices_ko.pdf): 정보의 외부 제3자 제공은 승인 필요, 개인가입자는 자기 자산 투자 목적이며 제3자에게 분배·제공하지 않을 것(제7조), 제한적 재분배는 비정기·비체계적일 때만(제10조), "가공지표 산출"은 신고 대상 이용 유형(제8조, 실시간 정보 기준).
- [공공데이터 분쟁조정 2014-006](https://www.data.go.kr/odmc/trublMdat/mdatCase/board.do?id=32): 거래소는 상업 이용에 이용료·계약을 요구했고 제3자의 무권한 재분배 고지가 조정에 포함됨.
- 네이버: `finance.naver.com`, `m.stock.naver.com` 의 robots.txt 는 모든 크롤러에 `Disallow: /`. [이용약관](https://policy.naver.com/policy/service.html)에는 자동화 수단 금지 열거 조항과 "타인 콘텐츠는 저작권법 허용 범위 또는 권리자 허락 필요" 문구. 금융 데이터 별도 약관·정보 제공처 표기는 **확인하지 못함**(에프앤가이드 약관도 못 찾음).
- FinanceDataReader: 코드는 MIT, 데이터 이용 안내는 없음. 저작권법 제93조(데이터베이스제작자의 권리)는 반복적·체계적 복제가 통상 이용과 충돌하면 상당한 부분의 복제로 본다(최신 개정은 확인 못함).
- 결론: 파생 값 공개를 **허용하는 조항은 어디에도 없었고**, 금지한다고 확정할 조항도 없었다. 그래서 공개하지 않는다. **자동 수집 자체의 위험은 비공개로 바꿔도 남는다**(robots.txt Disallow, KRX 제10조 ②호).

**보안 확인**(비로그인 REST 요청, 읽기 전용·존재하지 않는 경로 위주, 문서 내용은 읽지 않음)
- 새 컬렉션 `multifactor_private/…` 은 비로그인 읽기가 **허용(404)** 됨 → 새 이름의 컬렉션에 두면 공개된다. 그래서 비로그인 403 이 확인된 `chatgpt_macro_private/…` 아래에 둔다(문서·목록 조회 모두 403).
- **이 작업과 별개로**, `records_meta`, `records_todos`, `record_followups`, `ai_users` 컬렉션은 비로그인 목록 조회가 **HTTP 200** 이었다(문서 이름만 세고 내용은 읽지 않음. `records` 는 403). Firestore 규칙은 저장소에 없고 콘솔에서 관리되는 것으로 보여 코드로 고치지 않았다. **Firebase 콘솔의 Firestore 규칙을 직접 확인해야 한다.**
- 공개 저장소의 Actions 아티팩트·Summary 는 누구나 볼 수 있다. 이전 시험 실행의 결과 아티팩트 `multifactor-kr-result` 2개는 삭제했고, 이제 워크플로는 결과 아티팩트를 올리지 않으며 `mf-verify` 도 집계만 Summary 에 쓴다. **이전 `mf-verify` 실행(run 39227126029)의 Summary 에는 종목별 네이버 분기 금액 표가 남아 있다**(삭제하지 않음, 필요하면 실행 기록 삭제).

## 병합 후 해야 할 일

순서대로 확인한다. **아래 단계는 모두 병합 뒤에야 실제로 실행되며, 지금까지 실행해 본 적이 없다.**
1. 병합하면 `MF Private Deploy` 가 자동 실행되어 `mfLatest` 를 배포한다. 시험이 통과하고 "토큰 없음 401 · 잘못된 토큰 401 · GET 405" 확인이 통과하는지 본다. `MACRO_OWNER_UID` 비밀값이 새 함수에 연결되는지는 배포 로그에서 확인한다.
2. **서비스 계정 쓰기 권한 확인**(미확인): `GCP_SERVICE_ACCOUNT_KEY` 가 Firestore 에 쓸 수 있는지 시험 문서로 확인한다(운영 Firestore 에 시험 문서를 만들었다 지움 — 사용자 허락 후). 권한이 없으면 최소 권한(`roles/datastore.user`) 전용 서비스 계정 키를 사용자가 만들어 새 비밀값으로 넣고 워크플로의 인증 단계를 바꾼다.
3. `Actions → Multifactor KR → Run workflow` 로 1회 실행(약 17분). 게시 → "비로그인 접근 403" 확인 단계까지 통과하는지 본다. 이 확인이 실패하면 게시된 데이터가 공개되었을 수 있으니 즉시 해당 경로를 삭제하고 규칙을 점검한다.
4. 휴대폰·PC 에서 공식 주소를 열어 **본인 Google 로그인 → 결과 표시 → 로그아웃 → 데이터가 사라지는지** 확인하고, 다른 Google 계정으로 로그인하면 "본인 계정이 아닙니다"가 나오는지 확인한다(실제 로그인은 자동화할 수 없어 사용자가 한다).
5. Firebase 콘솔에서 Firestore 규칙을 점검한다(위 "보안 확인"의 공개 읽기 컬렉션).
6. 허브 화면(`regime-lite-v1.html`)에서 `multifactor.html` 로 가는 링크는 **추가하지 않았다.** 필요하면 별도 변경으로 한다.
